## Week 1 — Language & Backend Foundations

I built a C# console Task Manager that does full CRUD on a Tasks table in SQL Server.

**Courses:** C# Essential Training · .NET Core Essential Training · SQL Server Essential Training

**Practice: what I built**

- Ran SQL Server 2022 in Docker on my laptop and connected to it from C#.
- On startup, the app creates the `TaskManagerDB` database and the Tasks table if they don't exist yet.
- A menu lets you add, view, complete and delete tasks.
- I split the code into layers: `Models` (`TaskItem`, `WorkTask`, `FamilyTask`), `Repository` (`ITaskRepository`, `TaskRepository`), `Services` (`TaskService`) and `Data` (`DatabaseInitilizer`, connection factory).

**What I learned**

- The C# basics: types, classes, interfaces, inheritance and `using` for cleaning up connections.
- C# is the language and .NET is the platform (SDK, runtime and libraries) that runs it.
- The repository pattern keeps SQL out of the menu code, so each part is easier to change.
- You connect to the `master` database to create a new database, then switch to the app's own database.
- Parameterised queries stop SQL injection.

## Week 2 — Web API & Frontend Basics

I turned the Week 1 CRUD idea into WetSeason, a full ASP.NET Core Web API with EF Core and a React frontend that lists, adds, edits and deletes incidents.

**Courses:** ASP.NET Core: Building RESTful APIs · Entity Framework Core Essential Training · React.js Essential Training

**Practice: what I built**

1. **GameStore API (warm-up):** an ASP.NET Core API on EF Core and SQLite, with models, DTOs, migrations, a repository, minimal-API endpoints and a controller, tested with a `.http` file.
2. **WetSeason API:** an ASP.NET Core (.NET 10) Web API on EF Core and SQL Server.
    - Models for communities, incidents, resources, resource assignments and users, with enums for status, type and role.
    - Controllers for auth, communities and incidents, with the logic in service classes.
    - DTOs for every request and response, and FluentValidation rules on new incidents.
    - JWT login with four roles: public user, field officer, coordinator and admin.
    - EF Core migrations that run automatically when the app starts.
3. **WetSeason React frontend:** React 19, Vite, Tailwind and React Router. It has login, register and an incident dashboard with full create, read, update and delete through the API.
4. **MSAL test app:** a small React app that signs in with a Microsoft (Entra ID) account using MSAL.

**What I learned**

- Entity vs DTO. Returning the `Incident` entity caused a circular JSON error (community → incidents → community). DTOs fixed it and keep password hashes out of responses.
- `DbContext` is the database session and each `DbSet` is a table. Migrations version the schema like code.
- Services and `DbContext` are registered as scoped, so each HTTP request gets its own.
- Authentication is who you are; authorisation is what you can do. 401 means not logged in; 403 means logged in but not allowed.
- In React, `useState` holds data and `useEffect` runs side effects like API calls.
- CORS has to allow the frontend's origin, or the browser blocks the API calls.

## Week 3 — Full Stack Integration & Deployment

I containerised WetSeason with Docker and deployed the full app (API, frontend and database) to Azure, with a README covering setup, architecture and how to run it locally.

**Courses:** ASP.NET Core: MVC · Learning Docker · Azure Fundamentals (AZ-900 prep)

**Practice: what I built**

- **Dockerfiles:** a two-stage backend image (the .NET SDK builds it, then only the ASP.NET runtime ships) and a two-stage frontend image (Node builds it, then nginx serves the static files).
- **Docker Compose:** one command (`docker compose up -d --build`) starts SQL Server, the backend with hot reload, and the frontend on one network. SQL Server has a health check, so the backend waits until the database is ready.
- **Azure deployment:**
    - Frontend on **Azure Static Web Apps** (free tier, HTTPS, deploys from GitHub).
    - Backend container on **Azure App Service**, pulled from Azure Container Registry.
    - Database on **Azure SQL Database** (serverless).
- **CI/CD:** GitHub Actions builds and deploys the frontend on every push. I scoped the trigger so it only runs when frontend files change.
- **README:** covers the tech stack, how to run it locally, why I picked these Azure services over one VM, an architecture diagram, and the 10 problems I hit while deploying and how I fixed each one.

**What I learned**

- An image built on my Mac (Apple chip) is `arm64`, but Azure runs `amd64`. I had to build with `--platform linux/amd64`.
- Azure couldn't pull my image until I gave it registry credentials.
- App Service has two port settings, and the wrong one (80) silently overrode `WEBSITES_PORT=8080`.
- A React app needs a navigation fallback (`staticwebapp.config.json`), or refreshing a page gives a 404.
- CORS origins should come from config, so local and Azure can use different values.
- In the MVC course I learned how controllers, routing and model binding work. My API uses the same controller pattern, without views.

## Week 4 — Advanced Enterprise UI, Next.js & Modern Dev Workflows

I built a second WetSeason frontend: a management portal in Next.js (App Router) with a KendoReact data grid, scaffolded with AI-assisted development and connected to my ASP.NET Core API.

**Courses:** Next.js Essential Training · "Vibe coding" / AI-assisted development practices

**Practice: what I built**

- **Server-side rendering:** the incidents page is a server component. It reads the JWT from a cookie, fetches incidents and communities from the API on the server, and sends ready-made HTML to the browser.
- **Client components:** only the interactive parts use `"use client"`: the incident board, the create/edit form, the confirm dialog and the login form.
- **Kendo UI:** incidents show in a KendoReact `Grid` with the Meridian theme, alongside stat cards, a confirm dialog and toast messages.
- **Server Actions:** login, create, update and delete run as Next.js Server Actions, which call the ASP.NET Core API and refresh the page.
- **Safer login:** the JWT is stored in an `httpOnly` cookie, so browser JavaScript can never read it.
- **AI-assisted development:** I used Claude Code to scaffold the portal's CRUD views and API calls. I wrote a `CLAUDE.md` file telling the AI to keep the code simple and to explain every change, so I understood and checked everything before committing it.

**What I learned**

- **SSR vs client hydration:** the server sends HTML first, then React "hydrates" it in the browser to make it interactive.
- Server components can't use state or click handlers. That's what client components are for.
- Commercial component libraries like Kendo give you grids, sorting and paging without building them yourself, but they need a licence.
- AI tools work much better with project context (like `CLAUDE.md`), and I still have to review and test what they produce.

## Week 5 — Resiliency, Logging, Workflows & Linux Containers

I added structured logging with Serilog and Seq, exception tracking with Exceptionless, and SMTP email through MailKit, run as a Temporal workflow that retries if sending fails.

**Topics & tools:** Seq · log4net · Serilog / ILogger · Exceptionless · Temporal.io · MailKit / SMTP · Docker on Linux images

**Practice: what I built**

- **log4net first:** a rolling file appender writing to `logs/wetseason.log`, with a new file each day.
- **Then Serilog + Seq:** I replaced log4net with Serilog, configured from `appsettings.json`. It writes to the console and to a Seq server. My services log with message templates like `Incident {IncidentId} moved from {PreviousStatus} to {NewStatus}`, so Seq stores `IncidentId` as a field I can search and filter on.
- **Exceptionless:** catches unhandled exceptions from the API. I self-host it in Docker Compose, with Elasticsearch, Redis and a jobs container.
- **SMTP with MailKit:** when an incident is updated, the reporter gets an email built from an HTML template.
- **Temporal workflow:** sending the email runs as `IncidentUpdatedWorkflow`. The email is an activity that Temporal retries up to 5 times. If it still fails, a second activity records the permanent failure. The API starts the workflow and returns straight away, so the user isn't kept waiting.
- **Docker Compose:** Seq, Exceptionless and Temporal all run alongside SQL Server, the backend and the frontend. The frontend image and Redis use Alpine Linux, and the backend runs on the Linux ASP.NET runtime image.

**What I learned**

- Plain-text logs are hard to search. Structured logs keep each value as its own field, so I can filter, for example, every log for incident 42.
- Temporal remembers where a workflow got to. If the mail server or network drops, it retries the step instead of losing the email.
- A Temporal crash taught me two things. The address is a gRPC `host:port`, so adding `http://` breaks it. And a failed background service stops the whole ASP.NET host by default.
- Inside Docker, services reach each other by service name (`seq`, `temporal`), not `localhost`.
